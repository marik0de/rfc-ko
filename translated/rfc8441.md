## 1. 소개

HTTP(Hypertext Transfer Protocol) [RFC7230]는 서로 다른 버전 사이에 호환되는 리소스 수준의 의미론을 제공하지만, 연결 관리 수준의 호환성은 제공하지 않는다. 웹소켓(WebSocket)처럼 HTTP의 연결 관리 세부 사항에 의존하는 다른 프로토콜은 HTTP의 새 버전에 맞게 갱신되어야 한다.

웹소켓 프로토콜 [RFC6455]은 HTTP/1.1 업그레이드 메커니즘([RFC7230]의 6.7절)을 사용해 TCP 연결을 HTTP에서 웹소켓 연결로 전환한다. HTTP/2 [RFC7540]에서는 다른 방법을 써야 한다. HTTP/2는 다중화(multiplexing)라는 성질 때문에, `Upgrade`와 `Connection` 요청 헤더 필드나 `101 (Switching Protocols)` 응답 코드처럼 연결 전체에 적용되는 헤더 필드나 상태 코드를 허용하지 않는다. 이것들은 모두 [RFC6455]의 시작 핸드셰이크(opening handshake)에 필요하다.

> **역주:** RFC 7230의 6.7절(Upgrade)은 RFC 9110의 [7.8절](rfc9110.md#78-upgrade)로 옮겨졌다.

HTTP/2에서 웹소켓을 부트스트랩(bootstrap)할 수 있으면 TCP 연결 하나를 두 프로토콜이 함께 쓸 수 있고, HTTP/2의 더 효율적인 네트워크 사용을 웹소켓에도 넓힐 수 있다.

이 문서는 [RFC7540]의 8.3절에서 HTTP/2에 대해 규정한 HTTP `CONNECT` 메서드를 확장한다. 이 확장을 사용하면 `CONNECT`가 보통 연결 대상으로 삼는 외부 호스트 대신 새 프로토콜 이름을 연결 대상으로 넣을 수 있다. 그 결과 HTTP/2 스트림 하나 위에 터널이 생기며, 이 터널은 웹소켓(또는 다른 어떤 프로토콜)의 데이터를 실어 나를 수 있다. 그 연결의 다른 스트림은 확장 CONNECT 터널을 더 실을 수도, 기존 HTTP/2 데이터를 실을 수도, 둘을 섞어 실을 수도 있다.

> **역주:** RFC 7540의 8.3절(CONNECT 메서드)은 RFC 9113의 [8.5절](rfc9113.md#85-connect-메서드)이다.

이렇게 터널로 쓰이는 스트림은 그 연결의 다른 일반 스트림과 다중화되며, HTTP/2의 일반적인 우선순위, 취소, 흐름 제어 기능을 그대로 누린다.

스트림을 터널로 쓰고 이 문서에 정의한 시작 핸드셰이크 수정 사항을 사용해 웹소켓 연결을 성공적으로 맺은 스트림은, 그 뒤로 기존 웹소켓 프로토콜을 사용하며, 그 스트림을 웹소켓 명세의 TCP 연결인 것처럼 다룬다.

## 3. SETTINGS_ENABLE_CONNECT_PROTOCOL SETTINGS 매개 변수

이 문서는 [RFC7540]의 6.5.2절에 정의된 매개 변수에 새 `SETTINGS` 매개 변수를 하나 추가한다.

> **역주:** RFC 7540의 6.5.2절(정의된 설정)은 RFC 9113에서도 같은 번호의 절이다([6.5.2절](rfc9113.md#652-정의된-설정)).

새 매개 변수의 이름은 `SETTINGS_ENABLE_CONNECT_PROTOCOL`이다. 이 매개 변수의 값은 반드시 0 또는 1이어야 한다(MUST).

값이 1인 `SETTINGS_ENABLE_CONNECT_PROTOCOL`을 받은 클라이언트는 새 스트림을 만들 때 이 문서에 정의한 확장 CONNECT를 사용할 수 있다(MAY). 서버가 이 매개 변수를 받아도 아무 영향이 없다.

송신자는 앞서 값 1을 보낸 뒤에 값이 0인 `SETTINGS_ENABLE_CONNECT_PROTOCOL` 매개 변수를 보내서는 안 된다(MUST NOT).

`SETTINGS` 매개 변수를 사용해, 그렇게 하지 않으면 호환되지 않을 프로토콜 변경을 쓰겠다고 밝히는 것은 [RFC7540]의 5.5절에 정의된 "HTTP/2 확장(Extending HTTP/2)"의 한 사용 방식이다. 구체적으로, 새 의사 헤더 필드 `:protocol`을 추가하는 것과 [4장](#4-확장-connect-메서드)에서 `:authority` 의사 헤더 필드의 의미를 바꾸는 것에는 사용 동의 협상(opt-in negotiation)이 필요하다. 클라이언트가 `SETTINGS_ENABLE_CONNECT_PROTOCOL` 매개 변수를 먼저 받지 않고 이 문서에 정의한 확장 CONNECT 메서드의 규정을 사용하면, 이를 지원하지 않는 피어는 형식이 잘못된 요청을 감지하고 스트림 오류를 만들 것이다([RFC7540]의 8.1.2.6절).

> **역주:** RFC 7540의 5.5절(HTTP/2 확장)은 RFC 9113에서도 같은 번호의 절이다([5.5절](rfc9113.md#55-http2-확장)). RFC 7540의 8.1.2.6절(형식이 잘못된 요청과 응답)은 RFC 9113의 [8.1.1절](rfc9113.md#811-형식이-잘못된-메시지)이다.

## 4. 확장 CONNECT 메서드

HTTP/2에서 `CONNECT` 메서드를 사용하는 방법은 [RFC7540]의 8.3절에 정의되어 있다. 이 확장은 이 메서드를 다음과 같이 바꾼다.

- 새 의사 헤더 필드 `:protocol`을 요청 `HEADERS`에 포함할 수 있다(MAY). 이 필드는 `CONNECT`가 만든 터널에서 사용하려는 프로토콜을 나타낸다. 이 의사 헤더 필드는 값을 하나만 가지며, <https://www.iana.org/assignments/http-upgrade-tokens/>에 있는 "HTTP 업그레이드 토큰 레지스트리(Hypertext Transfer Protocol (HTTP) Upgrade Token Registry)"의 값을 담는다.
- `:protocol` 의사 헤더 필드가 들어 있는 요청에는 대상 URI([5장](#5-확장-connect로-웹소켓-프로토콜-부트스트랩하기) 참고)의 `:scheme`과 `:path` 의사 헤더 필드도 반드시 포함해야 한다(MUST).
- `:protocol` 의사 헤더 필드가 있는 요청에서 `:authority` 의사 헤더 필드는 [RFC7540]의 8.3절이 아니라 같은 문서의 8.1.2.3절에 따라 해석한다. 특히 서버는 이 확장으로 바뀌지 않은 `CONNECT` 메서드 요청을 처리할 때처럼 `:authority`가 나타내는 호스트로 터널을 만들어서는 안 된다(MUST NOT).

> **역주:** RFC 7540의 8.1.2.3절(요청 의사 헤더 필드)은 RFC 9113의 [8.3.1절](rfc9113.md#831-요청-의사-헤더-필드)이고, 8.3절(CONNECT 메서드)은 RFC 9113의 [8.5절](rfc9113.md#85-connect-메서드)이다.

`:protocol` 의사 헤더 필드가 있는 `CONNECT` 요청을 받은 서버는, 그 의사 헤더 필드가 나타내는 프로토콜 유형의 다른 서비스로 터널을 맺는다. 이 서비스는 서버와 같은 곳에 있을 수도 있고 그렇지 않을 수도 있다.

## 5. 확장 CONNECT로 웹소켓 프로토콜 부트스트랩하기

HTTP/2 스트림에서 웹소켓 연결을 시작하려면, `CONNECT` 요청에 `:protocol` 의사 헤더 필드를 반드시 포함해야 하며(MUST), 그 값은 반드시 "websocket"이어야 한다(MUST). 쿠키를 다루는 헤더 필드처럼 다른 HTTP 요청 헤더 필드와 응답 헤더 필드도 평소처럼 `CONNECT` 메서드와 함께 `HEADERS`에 포함할 수 있다. 이 요청은 [RFC6455]의 `GET` 기반 요청을 대신하며, 웹소켓 시작 핸드셰이크를 처리하는 데 쓰인다.

대상 URI([RFC7230]의 5.1절)의 스킴은 "wss" 스킴의 웹소켓이면 반드시 "https"여야 하고, "ws" 스킴의 웹소켓이면 반드시 "http"여야 한다(MUST). 대상 URI의 나머지 부분은 웹소켓 URI와 같다. 웹소켓 URI는 프록시 자동 구성에 여전히 쓰인다. 이 명세가 사용하는 HTTP/2 연결의 보안 요구 사항은 https 요청이면 [RFC7540]이, http 요청이면 [RFC8164]가 정한다.

> **역주:** RFC 7230의 5.1절(대상 리소스 식별)은 RFC 9110의 [7.1절](rfc9110.md#71-대상-리소스-결정)로 옮겨졌다.

[RFC6455]는 HTTP/2에 없는 `Connection`과 `Upgrade` 헤더 필드를 사용하도록 요구한다. 여기에 정의한 `CONNECT` 요청에는 이 헤더 필드를 포함해서는 안 된다(MUST NOT).

[RFC6455]는 `Host` 헤더 필드의 사용을 요구하는데, 이 필드 역시 HTTP/2에는 없다. 호스트 정보는 모든 HTTP/2 트랜잭션에 필요한 `:authority` 의사 헤더 필드의 일부로 전달된다.

웹소켓을 부트스트랩하는 데 이 확장 CONNECT를 사용하는 구현은 [RFC6455]의 `Sec-WebSocket-Key`와 `Sec-WebSocket-Accept` 헤더 필드를 처리하지 않는다. 그 기능은 `:protocol` 의사 헤더 필드가 대신하기 때문이다.

`Origin` [RFC6454], `Sec-WebSocket-Version`, `Sec-WebSocket-Protocol`, `Sec-WebSocket-Extensions` 헤더 필드는 [RFC6455]에 정의된 대로 `CONNECT` 요청 헤더 필드와 응답 헤더 필드에 쓰인다. HTTP/1의 헤더 필드 이름은 대소문자를 구분하지 않았지만, HTTP/2에서는 소문자로 인코딩해야 한다는 점에 유의하라.

시작 핸드셰이크를 성공적으로 처리한 뒤, 피어는 `CONNECT` 트랜잭션의 HTTP/2 스트림을 [RFC6455]가 말하는 TCP 연결인 것처럼 사용해 웹소켓 프로토콜 [RFC6455]을 진행하는 것이 좋다. 이 시점의 웹소켓 연결 상태는 [RFC6455]의 4.1절에 정의된 OPEN이다.

HTTP/2 스트림을 닫는 것도 [RFC6455]의 TCP 연결 종료에 대응한다. TCP 수준의 질서 있는 종료(orderly closure)는 `END_STREAM` 플래그([RFC7540]의 6.1절)로 나타낸다. RST 예외는 `CANCEL` 오류 코드([RFC7540]의 7장)를 담은 `RST_STREAM` 프레임([RFC7540]의 6.4절)으로 나타낸다.

> **역주:** RFC 7540의 6.1절(DATA), 6.4절(RST_STREAM), 7장(오류 코드)은 RFC 9113에서도 같은 번호의 절이다([6.1절](rfc9113.md#61-data), [6.4절](rfc9113.md#64-rst_stream), [7장](rfc9113.md#7-오류-코드)).

### 5.1. 예

```
[[ From Client ]]                       [[ From Server ]]

                                        SETTINGS
                                        SETTINGS_ENABLE_CONNECT_[..] = 1

HEADERS + END_HEADERS
:method = CONNECT
:protocol = websocket
:scheme = https
:path = /chat
:authority = server.example.com
sec-websocket-protocol = chat, superchat
sec-websocket-extensions = permessage-deflate
sec-websocket-version = 13
origin = http://www.example.com

                                        HEADERS + END_HEADERS
                                        :status = 200
                                        sec-websocket-protocol = chat

DATA
WebSocket Data

                                        DATA + END_STREAM
                                        WebSocket Data

DATA + END_STREAM
WebSocket Data
```

> **역주:** 왼쪽 열은 클라이언트가(From Client), 오른쪽 열은 서버가(From Server) 보내는 프레임이다. "WebSocket Data"는 웹소켓 데이터를 나타낸다.

## 6. 설계 고려 사항

HTTP/2에 더 많은 기능을 추가하면, HTTP/2 고유의 방식에 더 밀접하게 통합하는 것도 물론 가능하다. 이 설계는 HTTP/2와 웹소켓을 함께 실행한다는 주된 관심사를 해결하면서도 해법의 복잡도를 가장 낮추기 위해 선택되었다.

## 7. 중개자에 대하여

이 문서는 웹소켓이 HTTP 포워드 프록시(forward proxy)와 상호 작용하는 방식을 바꾸지 않는다. 웹소켓을 사용하려는 클라이언트가 HTTP/2로 HTTP 프록시에 연결한다면, 그 클라이언트는 그 프록시를 거쳐 HTTP로 웹소켓 서버까지 터널을 만들기 위해 계속 기존 `CONNECT`(즉, `:protocol` 의사 헤더 필드가 없는 것)를 사용하는 것이 좋다.

그 터널에서 결과적으로 쓰이는 HTTP 버전에 따라, 웹소켓을 직접 시작할지 이 문서에 설명한 수정된 `CONNECT` 요청으로 시작할지가 정해진다.

## 8. 보안 고려 사항

[RFC6455]는 웹소켓이 아닌 클라이언트, 특히 XMLHttpRequest 기반 클라이언트가 웹소켓 연결을 만들 수 없게 한다. 이를 위한 주된 메커니즘은 XMLHttpRequest 기반 클라이언트가 만들 수 없는, `Sec` 접두사가 붙은 요청 헤더 필드를 사용하는 것이다. 이 명세는 그 우려를 두 가지 방법으로 해결한다.

- XMLHttpRequest는 `Sec` 접두사가 붙은 요청 헤더 필드뿐 아니라 `CONNECT` 메서드의 사용도 금지한다.
- 의사 헤더 필드의 사용은 연결에 종속되며, HTTP/2는 프로토콜 스택 밖에서 의사 헤더를 만드는 것을 결코 허용하지 않는다.

이 명세를 사용할 때의 웹소켓 프로토콜 사용에는 10.8절을 제외한 [RFC6455]의 10장 보안 고려 사항이 계속 적용된다. 그 절은 이 문서에서 바뀐 부트스트랩 핸드셰이크(bootstrapping handshake)에 국한된 것이라 관련이 없다.

## 9. IANA 고려 사항

### 9.1. 새 HTTP/2 설정

이 문서는 [RFC7540]의 11.3절이 만든 "HTTP/2 설정(HTTP/2 Settings)" 레지스트리에 항목 하나를 등록한다.

- 코드(Code): 0x8
- 이름(Name): SETTINGS_ENABLE_CONNECT_PROTOCOL
- 초기값(Initial Value): 0
- 명세(Specification): This document

> **역주:** RFC 9113은 RFC 7540이 만든 레지스트리를 다시 정의하지 않으며, IANA는 "HTTP/2 설정" 레지스트리에서 RFC 7540에 대한 참조를 RFC 9113을 가리키도록 갱신했다(RFC 9113의 [11장](rfc9113.md#11-iana-고려-사항)).

### 9.2. 새 HTTP 업그레이드 토큰

이 문서는 [RFC7230]이 만든 "HTTP 업그레이드 토큰(HTTP Upgrade Tokens)" 레지스트리에 항목 하나를 등록한다.

- 값(Value): websocket
- 설명(Description): The Web Socket Protocol
- 예상 버전 토큰(Expected Version Tokens):
- 참조(References): [RFC6455] [RFC8441]

> **역주:** 이 레지스트리는 현재 RFC 9110의 [16.7절](rfc9110.md#167-업그레이드-토큰-레지스트리)에 정의되어 있다.

> **역주:** 9.1절과 9.2절의 IANA 등록 명세에서 항목 값은 원문 그대로 두고, 항목 이름만 번역해 원어를 병기했다.
